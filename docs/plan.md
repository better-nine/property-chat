## 1주차 — 세 공급자 API 직접 호출

목표는 "API를 실제로 붙여봤다"를 말할 수 있게 되는 것입니다. 같은 질문을 OpenAI, Anthropic, Gemini에 보내고 스트리밍으로 받으며, 호출마다 토큰 수와 비용을 남깁니다.

### 알아야 할 개념

- 메시지 역할: system(지시), user(사용자), assistant(모델 응답). 대화 기록은 서버가 아니라 호출하는 쪽이 매번 통째로 보냅니다.
- 토큰: 과금과 길이 제한의 단위. 입력 토큰과 출력 토큰 단가가 다릅니다.
- `max_tokens`, `temperature`, 컨텍스트 윈도우
- 스트리밍: 응답을 한 번에 받지 않고 조각(청크)으로 받음. 첫 토큰까지 걸리는 시간이 체감 속도를 좌우합니다.
- 세 SDK는 요청/응답 모양이 조금씩 다릅니다. 이 차이를 몸으로 겪어보는 것이 2주차 추상화의 재료입니다.

## 2주차 — 공급자 추상화 + 로컬 LLM

목표는 설정값 하나로 공급자를 바꾸는 구조를 만드는 것입니다. Java에서 인터페이스와 구현체를 나누던 경험이 가장 잘 드러나는 주차입니다.

### 설계

- 공통 타입(dataclass): `Message`, `ToolCall`, `LLMResponse`(텍스트, tool 호출, 토큰, 비용, 지연시간)
- `LLMProvider` 추상 클래스(ABC 또는 Protocol): `chat(messages, tools=None)`, `stream(messages, tools=None)`
- 구현체: `OpenAIProvider`, `AnthropicProvider`, `GeminiProvider`, `OllamaProvider`, (선택) `BedrockProvider`
- 팩토리: 환경변수 `LLM_PROVIDER`, `LLM_MODEL`을 읽어 구현체 생성
- 1주차 비용·지연 로깅은 구현체마다 넣지 말고 공통 래퍼(데코레이터) 한 곳에서 처리

### 할 일

- [ ] 1주차 스크립트 3개를 구현체 3개로 옮기기
- [ ] Ollama 설치 → 작은 모델 1~2개 `ollama pull` (PC 메모리에 맞는 크기로)
- [ ] `OllamaProvider` 작성. Ollama는 OpenAI 호환 엔드포인트(`localhost:11434/v1`)를 제공하므로 OpenAI SDK를 재사용할 수 있음

## 3주차 — 중개보수 계산·실거래가 조회 tool

목표는 "계산과 데이터 조회는 코드가, 설명은 LLM이" 나눠 맡는 구조를 만드는 것입니다. LLM은 금액 구간 판단과 한도액 적용을 자주 틀리고, 최신 시세는 아예 모릅니다. 그래서 이 두 가지를 tool로 빼야 하는 이유를 직접 보여줄 수 있습니다.

### tool use 동작 순서

1. 요청과 함께 tool 목록(이름, 설명, 입력 JSON Schema)을 보냄
2. 모델이 텍스트 대신 "이 tool을 이 인자로 호출해달라"는 응답을 돌려줌 (OpenAI는 `tool_calls`, Anthropic은 `tool_use` 블록)
3. 내 코드가 함수를 실행하고 결과를 대화에 추가해 다시 보냄 (OpenAI는 `tool` 역할 메시지, Anthropic은 `tool_result` 블록)
4. 모델이 최종 답을 낼 때까지 2~3을 반복. 무한 반복을 막기 위해 최대 횟수(예: 5회)를 걸어둠

### tool 1: 중개보수 계산 `calculate_brokerage_fee`

- 입력: 거래 종류(매매·교환, 임대차), 대상물(주택, 오피스텔, 그 외), 거래금액 또는 보증금·월세
- 출력: 상한요율, 한도액, 상한 중개보수, 적용한 근거
- 월세는 환산보증금으로 계산: 보증금 + 월세 × 100, 그 합계가 5천만원 미만이면 보증금 + 월세 × 70
- 요율·한도액은 공인중개사법 시행규칙 별표와 시·도 조례 기준으로 확인. 오피스텔은 요건에 따라 별도 요율, 주택 외는 상한 안에서 협의
- 요율표는 코드에 박지 말고 설정 데이터(YAML 등)로 분리. 법이 바뀌면 데이터만 고치면 되고, 면접에서 말하기 좋은 설계 포인트
- 시험 범위(중개사법령 및 실무)와도 겹쳐서 공부가 됩니다

### tool 2: 실거래가 조회 `get_apt_trades`

- 공공데이터포털의 국토교통부 아파트 매매 실거래가 API 활용 (활용 신청 필요)
- 입력: 지역(법정동 코드), 계약 년월, (선택) 단지명 / 출력: 거래일, 단지, 전용면적, 층, 거래금액
- 사용자는 "마포구"처럼 말하므로 지역명 → 법정동 코드 변환 함수 필요
- 외부 API라서 타임아웃, 에러 코드 처리, 같은 조회는 하루 동안 캐시. 은행 연동 경험을 그대로 보여줄 수 있는 부분
- 결과가 길면 요약(건수, 최저·최고·중위값 + 최근 10건)해서 모델에 전달 (토큰 절약)

## 4주차 — FastAPI SSE + 채팅 화면

목표는 CLI를 웹 서비스로 바꾸는 것입니다. 브라우저에서 답이 글자 단위로 흘러나오고, tool 실행 중에는 "실거래가 조회 중" 같은 상태가 보여야 합니다.

### 설계

- `POST /api/chat`: 요청 본문은 대화 기록, 응답은 `text/event-stream` (FastAPI `StreamingResponse`)
- 이벤트 종류를 나눠서 보내기: `token`(텍스트 조각), `tool_start`, `tool_end`, `done`(토큰·비용 포함), `error`
- 브라우저 기본 `EventSource`는 GET만 지원하므로, `fetch` + `ReadableStream`으로 직접 파싱
- 대화 기록은 우선 프론트 상태에 두고, 7주차에 필요하면 DB로 옮김

### 할 일

- [ ] FastAPI 프로젝트 구성, Pydantic 요청/응답 모델
- [ ] 3주차 tool 루프를 제너레이터로 바꿔 이벤트를 `yield`
- [ ] 스트리밍 중 에러 처리: 이미 200을 보낸 뒤이므로 HTTP 상태코드 대신 `error` 이벤트로 알림
- [ ] 클라이언트 연결 끊김 감지 → LLM 스트림도 중단 (안 하면 토큰 비용이 계속 나감)
- [ ] Vite + React + TypeScript로 채팅 화면 1장: 메시지 목록, 입력창, 스트리밍 표시, tool 상태 표시
- [ ] 이벤트 타입을 TypeScript 유니언 타입으로 정의
- [ ] 사용자가 입력한 주소·금액은 로그에서 마스킹, 답변 아래에 "법률 자문이 아닌 참고 정보" 안내 고정

### 완료 기준

로컬 브라우저에서 채팅하면 답이 스트리밍되고, tool 호출 상태가 보이며, 답이 끝나면 토큰·비용이 작게 표시됩니다.

### 면접용으로 정리해둘 것

SSE와 WebSocket의 차이, 그리고 LLM 응답에 SSE를 고른 이유 (서버에서 클라이언트로만 흐르고, HTTP 그대로라 프록시·인증이 단순함).

## 5주차 — RAG 전반부: 법령 수집·청킹·임베딩

목표는 공인중개사법 조문을 벡터 DB에 넣고, 질문과 의미가 가까운 조문을 찾아오는 것입니다. 답변 생성은 6주차에 합니다.

### RAG 파이프라인 전체 그림

1. 수집: 원문 가져오기
2. 전처리·청킹: 검색 단위로 자르기
3. 임베딩: 각 청크를 벡터(숫자 배열)로 변환
4. 저장: 벡터 DB에 저장 (여기까지 5주차)
5. 검색: 질문도 벡터로 바꿔 가까운 청크를 찾기
6. 생성: 찾은 청크를 프롬프트에 넣고 답변 (5~6은 6주차)

### 데이터

- 대상: 공인중개사법, 같은 법 시행령·시행규칙. 여유가 있으면 부동산 거래신고 등에 관한 법률도
- 출처: 국가법령정보센터. Open API(사용 신청 필요)나 원문 다운로드
- 법령 원문은 저작권 보호 대상이 아니라서 공개 저장소에 넣어도 문제가 없습니다. 시험 문제집·강의 자료는 넣지 마세요.

### 할 일

- [ ] 수집 스크립트: 법령 원문 → JSON (법령명, 조 번호, 조 제목, 본문, 시행일)
- [ ] 청킹: 조 단위가 기본. 긴 조는 항 단위로 나누되, 각 조각 앞에 "공인중개사법 제32조(중개보수 등)" 같은 제목을 붙여서 맥락 유지
- [ ] pgvector: Docker로 `pgvector/pgvector` 이미지 실행, `chunks` 테이블 (id, law, article_no, title, content, embedding, metadata)
- [ ] 임베딩 모델 2개 준비: OpenAI `text-embedding-3-small`, Ollama `bge-m3` (다국어 오픈소스). 모델마다 벡터 차원이 다르니 테이블이나 컬럼을 나눠서 저장
- [ ] 적재 스크립트는 여러 번 돌려도 안전하게 (중복 저장 없이 갱신)
- [ ] HNSW 인덱스 생성, 코사인 거리로 검색하는 `search(query, k)` 함수
- [ ] 검색 결과 눈으로 확인: "중개보수 한도", "중개사무소 개설등록 결격사유" 등 10개

### 완료 기준

`search("중개보수 한도")`를 호출하면 관련 조문 5개가 조 번호와 함께 나옵니다. 두 임베딩 모델로 모두 검색됩니다.

### 덧붙이기

이 검색기는 공인중개사 시험 공부에 바로 쓸 수 있습니다. 공부하다 생긴 질문을 6주차 평가셋에 모아두세요.

## 6주차 — RAG 후반부: 답변 생성·평가·Agent

목표는 근거 조문을 달아 답하는 RAG를 완성하고, 정확도를 숫자로 측정해 개선하는 것입니다. 이 주차의 평가 숫자가 포트폴리오에서 가장 큰 차별점입니다.

### 답변 생성

- [ ] 프롬프트 조립: 검색된 조문을 번호를 붙여 넣고, "제공된 조문으로만 답하고 근거를 [법령명 제N조]로 표시, 없으면 모른다고 답할 것" 지시
- [ ] 답변 아래에 참고한 조문 목록을 화면에 표시 (`sources` 이벤트)
- [ ] "조문에 없는 질문"에 모른다고 답하는지 확인 (환각 테스트)

### 평가셋과 측정

- [ ] 질문 20개 직접 작성: 질문, 정답 조 번호, 모범 답 한 줄 (CSV)
- [ ] 검색 지표: hit@5 = 정답 조문이 상위 5개 안에 들어온 비율
- [ ] 답변 지표: 정답 여부를 직접 채점하거나 LLM에게 채점시키기 (LLM-as-judge). 둘의 결과가 얼마나 일치하는지도 확인
- [ ] `eval.py` 한 번 실행으로 전체 지표 출력

### 개선 실험 (하나씩 바꾸고 매번 측정)

| 실험 | 바꾸는 것 | hit@5 | 답변 정확도 |
| --- | --- | --- | --- |
| 기준선 | 조 단위 청크, k=5 |  |  |
| 청크 크기 | 항 단위로 더 잘게 |  |  |
| 임베딩 모델 | OpenAI vs bge-m3 |  |  |
| 하이브리드 검색 | 벡터 + 키워드(예: pg_trgm) |  |  |
| 질문 재작성 | LLM이 질문을 법률 용어로 바꿔 검색 |  |  |

### Agent로 묶기

- [ ] 검색을 `search_law(query)` tool로 등록
- [ ] 이제 모델이 질문을 보고 `calculate_brokerage_fee`, `get_apt_trades`, `search_law` 중 무엇을 쓸지 스스로 고름
- [ ] tool을 여러 단계로 이어 쓰는지 확인 (예: "마포구 84㎡ 아파트를 최근 실거래가로 사면 중개보수 상한은? 근거 조문도"처럼 조회 → 계산 → 법령 검색이 이어지는 질문)

### 완료 기준

표의 빈칸이 모두 채워져 있고, 기준선 대비 개선된 숫자가 있습니다. 채팅 화면에서 계산·시세·법령 질문을 섞어 물어도 알맞은 tool이 호출됩니다.

## 7주차 — 운영: 안정성·모니터링·배포

목표는 "만들어봤다"를 "운영해봤다"로 바꾸는 것입니다. 은행 연동 시스템을 운영한 경험이 그대로 연결되는 주차입니다. 외부 API 장애 대응은 이미 해본 일입니다.

### 안정성

- [ ] 타임아웃: 첫 토큰까지, 전체 응답을 따로 설정
- [ ] 재시도: 429·5xx에만 지수 백오프 (`tenacity` 등). 4xx는 재시도하지 않음
- [ ] 폴백: 주 공급자 장애 시 다른 공급자로 자동 전환 (2주차 추상화 덕분에 설정만으로 가능)
- [ ] 비용 상한: 일일 누적 비용을 DB에 저장하고, 넘으면 요청 차단 + 안내 메시지
- [ ] IP별 요청 수 제한 (공개 URL이므로 필수)

### 모니터링

- [ ] Langfuse: Docker로 셀프호스팅하거나 클라우드 무료 플랜. Python SDK의 `@observe` 데코레이터로 검색·LLM 호출·tool 실행을 하나의 트레이스로 묶기
- [ ] Langfuse에서 볼 것: 요청별 토큰·비용·지연, 어느 단계가 느린지, 나쁜 답이 나온 요청의 프롬프트
- [ ] 6주차 평가셋을 Langfuse 데이터셋으로 옮겨두면 프롬프트를 바꿀 때마다 비교 가능
- [ ] Sentry: FastAPI 연동으로 예외 수집
- [ ] (선택) Prometheus + Grafana로 요청 수·지연시간 대시보드

### 배포

- [ ] 백엔드 Dockerfile, 프론트 빌드, `docker-compose.yml` (api + postgres + 프론트를 서빙하는 nginx)
- [ ] AWS EC2 작은 인스턴스에 배포. 비용을 아끼려면 RDS 대신 같은 서버의 Postgres 컨테이너
- [ ] Ollama는 GPU가 없는 서버에서 느리므로 배포본은 상용 API만 사용 (로컬에서는 그대로 지원)
- [ ] API 키는 환경변수나 AWS SSM Parameter Store에 보관. 이미지에 넣지 않음
- [ ] HTTPS와 도메인 (선택)
- [ ] GitHub Actions로 테스트 자동 실행 (선택)

### 완료 기준

공개 URL에서 채팅이 동작합니다. Langfuse에 요청별 트레이스가 쌓입니다. 주 공급자 키를 일부러 틀리게 바꿔도 폴백으로 답이 나옵니다.
