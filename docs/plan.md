## 개요

10주 동안 Spring Boot로 "AI 부동산 상담 챗봇"(`property-chat`)을 만들며, LLM 연동 경험과 Spring 백엔드 기본기를 함께 쌓습니다. 목표 완료는 2027년 2월 말(버퍼 포함 3월 중순)이고, 배포 URL·GitHub 저장소·블로그 글 1편·주차별 설계 기록이 남습니다.

## 1주차 — 프로젝트 생성 + API 직접 호출

목표는 라이브러리 없이 HTTP로 OpenAI·Anthropic을 직접 호출해서, LLM API가 실제로 어떻게 생겼는지 아는 것입니다. Spring AI는 2주차에 들어오는데, 그 안에서 무슨 일이 일어나는지 설명할 수 있게 하려는 주차예요.

**Spring 기본기: 설정 관리**

### 알아야 할 개념

- LLM API: 메시지 역할(system, user, assistant), 토큰(입력·출력 단가가 다름), `max_tokens`, `temperature`. 대화 기록은 호출하는 쪽이 매번 통째로 보냄
- `application.yml`과 프로필(`local`, `prod`): 환경별로 설정을 나누는 이유
- `@ConfigurationProperties`: 설정값을 타입이 있는 객체(record)로 묶기. `@Value`를 여기저기 뿌리는 것보다 나은 이유
- 비밀값은 코드·yml에 쓰지 않고 환경변수로 주입 (`${OPENAI_API_KEY}`)
- HTTP 클라이언트: `RestTemplate`(구형) / `RestClient`(동기, 권장) / `WebClient`(비동기)의 차이

### 할 일

- [ ] Spring Initializr로 `backend/`에 프로젝트 생성: Gradle, Java 21 이상, Spring Boot 최신 안정 버전. 의존성은 Spring Web, Validation, Actuator만 (Spring AI는 2주차에)
- [ ] `application.yml` + `application-local.yml` 분리, API 키는 환경변수로 받기 (IntelliJ 실행 설정의 환경변수 사용)
- [ ] `LlmProperties` record를 `@ConfigurationProperties(prefix = "llm")`로 만들기 (공급자별 baseUrl, apiKey, model, timeout). `@Validated` + `@NotBlank`로 키가 없으면 기동 실패하게
- [ ] `RestClient`로 OpenAI와 Anthropic을 각각 호출. 요청·응답은 record DTO로 정의 (두 공급자의 모양이 어떻게 다른지 기록)
- [ ] 응답의 usage에서 입력·출력 토큰을 꺼내 비용(원) 계산. 단가는 각 사 가격 페이지를 보고 설정 파일에
- [ ] 임시 엔드포인트 `POST /api/dev/ask?provider=openai` → 답, 토큰, 비용, 지연시간을 JSON으로 반환
- [ ] 스트리밍은 curl로 `stream: true`를 호출해 응답 형태만 눈으로 확인 (구현은 5주차)

## 2주차 — Spring AI 도입 + 계층 설계

목표는 1주차의 직접 호출을 Spring AI로 바꾸면서, 코드를 Controller · Service · 외부 연동으로 나누고 처음으로 테스트를 짜는 것입니다.

**Spring 기본기: 계층 설계, 의존성 주입, 단위 테스트**

### 알아야 할 개념

- 계층별 책임: Controller는 요청 검증과 응답 변환만, Service는 업무 흐름, 외부 연동 클래스는 API 호출만. Controller에 로직을 두면 왜 안 되는지
- 생성자 주입: 필드 주입(`@Autowired`)보다 나은 이유 (불변, 테스트 용이)
- 인터페이스로 외부 연동을 감싸는 이유: 공급자 교체, 테스트에서 가짜 구현 주입
- Spring AI의 `ChatModel`(모델별 구현)과 `ChatClient`(편의 API)의 차이, 같은 타입 빈이 여러 개일 때 `@Qualifier`
- 단위 테스트(Mockito) vs 슬라이스 테스트(`@WebMvcTest`) vs 통합 테스트(`@SpringBootTest`)

- [ ] 패키지 구조 정하기: 기능별(`chat`, `llm`, `tool`, `law`) vs 계층별 — 하나를 골라 이유를 기록

## 3주차 — 중개보수 계산 tool

목표는 "계산은 코드가, 설명은 LLM이" 나눠 맡는 구조를 만드는 것입니다. LLM은 금액 구간 판단과 한도액 적용을 자주 틀리므로, 계산을 tool로 빼고 그 로직을 테스트로 단단히 묶습니다.

**Spring 기본기: 도메인 로직 분리, 파라미터화 테스트, 설정 데이터 바인딩**

### tool use 동작 순서

1. 요청과 함께 tool 목록(이름, 설명, 입력 스키마)을 보냄
2. 모델이 "이 tool을 이 인자로 호출해달라"고 응답
3. 앱이 메서드를 실행하고 결과를 대화에 추가해 다시 보냄
4. 모델이 최종 답을 낼 때까지 반복

Spring AI는 이 루프를 대신 돌려줍니다. 메서드에 `@Tool`을 붙이면 돼요. 다만 면접에서는 이 순서를 직접 설명할 수 있어야 하니, 디버그 로그로 실제 요청·응답을 한 번 눈으로 확인하세요.

### 중개보수 계산 규칙

- 입력: 거래 종류(매매·교환, 임대차), 대상물(주택, 오피스텔, 그 외), 거래금액 또는 보증금·월세
- 출력: 상한요율, 한도액, 상한 중개보수, 적용 근거
- 월세는 환산보증금: 보증금 + 월세 × 100, 합계가 5천만원 미만이면 보증금 + 월세 × 70
- 요율·한도액은 공인중개사법 시행규칙 별표와 시·도 조례로 확인
- 시험 범위(중개사법령 및 실무)와 겹쳐서 공부가 됩니다

### 할 일

- [ ] 요율표를 `brokerage-fee.yml` 같은 설정 데이터로 분리하고 `@ConfigurationProperties`로 바인딩 (법이 바뀌면 데이터만 수정)
- [ ] `BrokerageFeeCalculator`: Spring에 의존하지 않는 순수 자바 클래스로 계산 로직 작성. 금액은 `long`(원) 또는 `BigDecimal` — `double`을 쓰면 안 되는 이유 기록
- [ ] 입력값 검증: 음수 금액, 지원하지 않는 대상물 → 명확한 예외
- [ ] `@ParameterizedTest` + `@CsvSource`로 케이스 15개 이상: 구간 경계 금액, 한도액 적용, 월세 70배 케이스. 기대값은 공개된 중개보수 계산기로 교차 확인
- [ ] `BrokerageFeeTool`: `@Tool` 메서드가 계산기를 호출. tool 설명문을 구체적으로 (모델은 이걸 보고 호출 여부를 정함)
- [ ] `ChatService`에 tool 등록, 디버그 로그로 tool 호출 과정 확인
- [ ] 비교 실험: tool 없이 중개보수 질문 10개를 물었을 때 틀린 비율 vs tool 사용 시 (블로그·이력서 숫자)

### 완료 기준

"보증금 5천에 월세 80만원이면 중개보수 상한은?"을 물으면 모델이 tool을 호출하고 정확한 금액으로 답합니다. 계산기 테스트는 Spring을 띄우지 않고 1초 안에 끝납니다.

## 4주차 — 실거래가 조회 tool + 예외 처리

목표는 외부 공공 API를 안전하게 붙이는 것입니다. 외부 API는 느리거나 죽거나 이상한 값을 줍니다. 그때 앱이 어떻게 동작하는지를 설계하는 것이 이 주차의 핵심이고, 은행 연동 업무와 가장 가까운 주차입니다.

**Spring 기본기: 예외 처리, 외부 연동 타임아웃, 캐시, 외부 API 테스트**

### 알아야 할 개념

- 예외를 어디서 잡고 어디서 던지나: 외부 연동 계층은 기술적 예외를 우리 예외로 바꿔 던지고, 전역 처리는 `@RestControllerAdvice` 한 곳에서
- 에러 응답 형식 통일: Spring의 `ProblemDetail`(RFC 7807)
- 타임아웃을 안 걸면 생기는 일 (스레드가 묶여 서비스 전체가 느려짐)
- 캐시: `@Cacheable`이 동작하는 원리(프록시)와 같은 클래스 안 호출에서 안 먹히는 이유

### 할 일

- [ ] 공공데이터포털 국토교통부 아파트 매매 실거래가 API 키로 응답 형식부터 curl로 확인
- [ ] `AptTradeClient`: `RestClient`에 연결·응답 타임아웃 설정, 응답을 record로 변환
- [ ] 지역명 → 법정동 코드 변환 (코드 파일을 리소스로 두고 조회)
- [ ] 예외 계층 설계: 예) `ExternalApiException`, `InvalidRegionException` + `@RestControllerAdvice`에서 `ProblemDetail`로 변환
- [ ] tool에서 예외가 나면 앱이 죽지 않고 모델에게 "조회 실패" 메시지를 돌려주기
- [ ] Caffeine 캐시 + `@Cacheable`: 같은 지역·월 조회는 하루 동안 재사용
- [ ] 결과가 길면 요약(건수, 최저·최고·중위값 + 최근 10건)해서 모델에 전달 (토큰 절약)
- [ ] `AptTradeTool`(`@Tool`) 등록
- [ ] 테스트: `MockRestServiceServer`(또는 WireMock)로 정상 응답 / 500 에러 / 타임아웃 세 경우 검증

## 6주차 — RAG 전반부 + DB

목표는 공인중개사법 조문을 벡터 DB(pgvector)에 넣고, 의미가 비슷한 조문을 찾아오는 것입니다. 같은 DB에 호출 기록 테이블도 만들어 JPA를 제대로 써봅니다.

**Spring 기본기: JPA 엔티티·리포지토리, 트랜잭션, Flyway 스키마 관리**

### RAG 파이프라인

1. 수집: 법령 원문 가져오기 (Python 스크립트)
2. 청킹: 조 단위로 자르기 (Python 스크립트 → JSON)
3. 임베딩 + 저장: Spring AI `VectorStore`에 적재 (여기까지 6주차)
4. 검색 → 답변 생성 (7주차)

### 알아야 할 개념

- 임베딩: 문장을 의미를 담은 숫자 배열로 바꾼 것. 의미가 비슷하면 벡터도 가까움
- JPA 엔티티 생명주기와 더티 체킹, 지연 로딩, N+1 문제 (면접 단골)
- `@Transactional`: 어디에 붙이는지, 왜 Service에 붙이는지, 읽기 전용 트랜잭션
- Flyway: DB 스키마도 코드처럼 버전 관리. `ddl-auto`를 운영에서 쓰면 안 되는 이유

### 할 일

- [ ] `docker-compose.yml`에 `pgvector/pgvector` 이미지로 Postgres 추가, Flyway 마이그레이션 `V1__init.sql`
- [ ] `ChatLog` 엔티티(공급자, 모델, 토큰, 비용, 지연시간, 생성 시각) + `JpaRepository`. 호출마다 저장 (8주차 비용 상한의 재료)
- [ ] `scripts/law_fetch.py`: 국가법령정보센터에서 공인중개사법·시행령·시행규칙 수집 → 조 단위 JSON (법령명, 조 번호, 제목, 본문, 시행일). 긴 조는 항 단위로 나누고 제목을 앞에 붙여 맥락 유지
- [ ] Spring AI pgvector 스타터 + OpenAI 임베딩 모델 설정
- [ ] `LawIngestionService`: JSON을 읽어 `VectorStore`에 적재. 조문별로 고정 ID를 두어 여러 번 돌려도 중복이 생기지 않게
- [ ] 검색 확인용 `GET /api/dev/law-search?q=` → 상위 5개 조문 + 유사도
- [ ] 눈으로 확인할 질문 10개 ("중개보수 한도", "개설등록 결격사유" 등)

### 완료 기준

`docker compose up` 후 적재를 돌리면 조문이 들어가고, 검색 API가 관련 조문을 돌려줍니다. 호출마다 `chat_log`에 행이 쌓입니다. 스키마는 Flyway로만 바뀝니다.
